# 产品校招方法论

## 使用原则

本文件仅在用户材料不足时提供产品岗位的出题与答题兜底，不覆盖用户明确提供的岗位要求、项目事实、个人职责、业务数据和结论。若框架与用户事实冲突，以用户事实为准；缺失信息必须标记 `【待补充】`，不得用方法论补造成个人经历。

## 核心目标

产品工作的核心是识别值得解决的问题，在用户价值、业务价值与实现成本之间做取舍，并通过可验证的方案推动结果。

- 判断问题是否真实、重要且适合当前阶段解决。
- 明确目标用户、使用场景和核心需求。
- 将需求转化为可交付、可衡量的产品方案。
- 协同设计、研发、运营等角色推进落地。
- 用数据和反馈验证效果，持续迭代。

## 业务链路

```text
业务目标 → 用户与场景 → 问题识别 → 需求验证 → 方案设计 → 优先级 → 协同交付 → 上线验证 → 复盘迭代
```

面试追问应沿链路展开：为什么做、服务谁、证据是什么、为何选此方案、如何取舍、怎样验收、结果能否归因。

## 能力模型

| 能力 | 校招考察重点 |
|---|---|
| 用户理解 | 能否区分用户表达、真实需求与解决方案 |
| 业务理解 | 能否说明产品动作如何影响业务目标 |
| 问题拆解 | 能否从现象拆到人群、场景、链路和原因 |
| 方案设计 | 能否覆盖主流程、异常流与关键状态 |
| 优先级判断 | 能否结合价值、成本、风险和依赖做取舍 |
| 数据意识 | 能否定义指标口径并验证方案效果 |
| 推进协作 | 能否澄清分工、处理分歧和推动交付 |
| 复盘迁移 | 能否识别误判并沉淀可复用的方法 |

## 指标

指标必须与产品类型和业务阶段匹配，不能机械套用。

- 结果指标：活跃、留存、转化、交易额、收入、满意度或任务成功率。
- 过程指标：曝光、点击、到达、完成、使用频次、关键功能渗透率。
- 体验指标：完成时长、错误率、退出率、投诉率、可用性评分。
- 护栏指标：退款、误触、打扰、性能、风险事件、长期留存损伤。
- 口径追问：统计对象、时间窗口、去重方式、基线、样本与数据来源。

## 项目深挖

```text
背景与目标 → 个人职责 → 问题证据 → 关键判断 → 方案与取舍 → 推进动作 → 指标结果 → 归因 → 复盘
```

重点核验：

- 用户本人做了什么，团队成果与个人贡献如何区分。
- 需求来自数据、访谈、反馈还是业务要求，各自证据强度如何。
- 被放弃的方案是什么，放弃依据是什么。
- 上线结果是否达到目标，是否存在同期活动等干扰因素。
- 如果重做，最先修改哪项判断或动作。

## 场景题

场景题先澄清目标、用户、阶段、资源和约束，再作答。

- 新功能使用率低：检查触达、理解、价值、门槛、稳定性和目标人群匹配。
- 转化提升但投诉上升：核对增量质量，定位受损人群并设置护栏。
- 需求很多但研发有限：按目标贡献、用户影响、紧急度、成本和依赖排序。
- 数据与访谈结论冲突：检查样本、口径和场景差异，再补充验证。
- AI 功能上线：说明业务任务、输入输出、评估、成本、风险与人工兜底。

## 答案框架

产品项目题：

```text
结论 → 背景目标 → 用户与问题证据 → 我的判断和动作 → 方案取舍 → 验证结果 → 风险与复盘
```

产品场景题：

```text
澄清目标与约束 → 拆解用户链路 → 提出关键假设 → 排定优先级 → 设计最小方案 → 指标验证 → 风险护栏
```

答案应优先使用用户事实；没有真实数据时说明验证计划，不虚构结果。

## 正反例

正例：

> 我先确认目标是提升首周激活，而不是单纯提高功能点击。根据用户反馈和漏斗数据，我把问题定位在首次配置门槛，并选择先简化主流程；上线后同时观察激活率、次周留存和误操作率。

反例：

> 我做了用户调研，设计了很多功能，最后数据提升明显。

反例的问题：目标、证据、个人动作、指标口径和归因均不清楚。

## 风险边界

- 不把公开产品分析写成用户参与过的项目。
- 不默认用户主导战略、完整商业闭环或跨团队决策。
- 不把“用户说想要”直接等同于真实需求。
- 不只看增长结果，必须关注体验、合规、公平和长期价值。
- 涉及 AI 时不得只谈准确率，必须说明幻觉、隐私、权限、成本和人工兜底。
- 方法论只用于补足结构；任何具体数字、角色、公司内部信息均须来自用户或可靠来源。
