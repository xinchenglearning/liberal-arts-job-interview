# 客户成功与项目交付校招方法论

## 使用原则

本文件仅作为客户成功与项目交付岗位面试出题、追问和答题的兜底框架，不覆盖用户提供的客户、产品、合同、里程碑、使用数据、续约金额、交付结果、个人职责和项目事实。用户事实与 JD 优先；信息缺失时使用 `【待补充】`，不得把通用服务动作、虚构客户反馈或假设续约结果包装成用户经历。

客户成功更关注客户价值实现、使用、健康度、续约与增购；项目交付更关注范围、进度、质量、成本、验收与风险。复合岗位应区分商业承诺、交付责任和客户经营责任。

## 核心目标

客户成功与项目交付的核心是把合同、产品或解决方案转化为客户可感知、可验证的业务价值，在范围、进度、质量、资源和关系之间取得平衡，推动稳定上线、有效使用、验收续约与长期合作。

- 对齐客户目标、成功标准、范围和关键里程碑。
- 建立清晰的角色、计划、沟通与问题管理机制。
- 推动产品配置、实施、培训、上线和用户采用。
- 持续识别客户健康风险并协调解决。
- 以真实价值支撑验收、续约、增购和案例沉淀。

## 业务链路

客户成功链路：

```text
销售交接 → 客户目标与成功标准 → 启动与入驻 → 配置/培训 → 上线采用 → 健康度监测 → 价值复盘 → 风险干预 → 续约/增购 → 经验沉淀
```

项目交付链路：

```text
合同与范围确认 → 项目启动 → 需求澄清 → 计划与资源 → 方案/配置/开发 → 测试与培训 → 上线切换 → 验收 → 运维移交 → 项目复盘
```

出题时需明确业务模式、客户类型、产品标准化程度、实施周期、合同边界和验收方式，避免默认所有客户问题都能由客户成功或项目经理单独解决。

## 能力模型

| 能力 | 校招考察重点 |
|---|---|
| 客户与业务理解 | 能否理解客户目标、用户角色、流程和成功标准 |
| 范围与需求管理 | 能否区分合同范围、真实需求、变更和优先级 |
| 项目规划 | 能否拆里程碑、任务、依赖、责任人和验收标准 |
| 推动协同 | 能否协调客户、销售、产品、研发、实施和支持团队 |
| 采用与价值 | 能否把上线转化为使用、业务效果和客户认可 |
| 问题与风险 | 能否发现信号、判断影响、升级止损并跟踪关闭 |
| 数据分析 | 能否使用进度、质量、使用和健康度数据判断状态 |
| 沟通管理 | 能否管理预期、同步事实、记录决策并处理冲突 |

## 指标

- 项目进度：里程碑达成率、按期上线率、周期偏差、任务逾期率。
- 范围与质量：需求变更率、缺陷数、返工率、测试通过率、验收一次通过率。
- 服务效率：响应时长、问题解决时长、工单关闭率、升级事件数。
- 使用采用：激活率、活跃率、关键功能使用率、培训完成率、使用深度。
- 客户健康：健康度评分、风险客户占比、满意度、NPS、关键人参与度。
- 商业结果：验收率、续约率、流失率、增购率、回款进度、毛利或交付成本。
- 护栏指标：过度定制、范围失控、团队负荷、重大故障、投诉、数据安全与承诺偏差。

上线不等于成功，活跃不等于价值，满意度也不能替代续约和业务成效；指标必须说明口径、周期、客户分层及归因边界。

## 项目深挖

```text
客户背景与目标 → 合同范围/成功标准 → 关键人和治理机制 → 计划与资源 → 我的职责 → 需求及风险处理 → 上线采用 → 验收/价值结果 → 续约或移交 → 复盘
```

重点追问：

- 客户购买或启动项目要解决什么业务问题，成功由谁定义。
- 销售承诺、合同范围和客户新增需求之间是否一致。
- 用户本人负责计划、需求、配置、培训、客户沟通还是问题协调，决策权在哪里。
- 关键里程碑、依赖和风险如何识别，延期由什么事实触发。
- 客户不使用是产品、培训、流程、关键人、组织变动还是价值不足。
- 续约或验收结果来自实际价值、合同约束、关系维护还是其他因素。

## 场景题

- 客户提出合同外紧急需求：确认业务影响和必要性，评估范围、成本与排期，走变更或提供替代方案。
- 项目上线延期：核实关键路径和责任依赖，形成恢复计划，透明同步影响并及时升级。
- 产品已上线但使用率低：按用户角色、关键场景、培训、流程阻力和产品体验拆解，制定采用计划。
- 客户对故障强烈不满：先止损并建立固定同步节奏，区分已知事实和待查原因，恢复后提供复盘与预防措施。
- 续约前客户称未看到价值：回到最初目标和成功标准，补齐使用与业务证据；若价值未实现，明确改进计划而非临时承诺。

## 答案框架

客户成功或项目交付题：

```text
客户目标与成功标准 → 范围和约束 → 我的职责 → 计划与治理 → 关键动作及协同 → 风险/变更处理 → 上线采用与价值证据 → 验收续约 → 复盘
```

客户或项目场景题：

```text
确认事实、影响和紧急度 → 对齐合同范围与客户目标 → 定位根因和关键路径 → 形成选项与取舍 → 明确责任和沟通节奏 → 指标验证 → 升级、止损与复盘
```

没有真实续约金额、使用指标、故障原因或客户反馈时，应说明验证方法和待补信息，不得写成确定成果。

## 正反例

正例：

> 我负责培训安排和问题清单维护，没有产品排期决定权。上线后我按用户角色查看关键功能使用，发现一线使用者完成培训但实际流程没有切换；我与客户负责人确认阻力后，先选择一个团队试运行，并把产品问题和内部流程问题分别跟踪。

反例：

> 我服务意识很强，经常满足客户的各种需求，最终客户非常满意并成功续约。

反例的问题：缺少客户目标、合同边界、个人职责、具体动作、价值证据和续约口径，还可能以无边界满足需求造成范围失控。

## 风险边界

- 不虚构客户名称、合同范围、上线时间、满意度、续约金额、使用数据或个人权限。
- 不把销售、产品、研发、实施和客户团队共同成果全部归为个人。
- 不为安抚客户承诺未经评估的功能、排期、赔偿、数据结果或服务范围。
- 不隐瞒延期、故障和重大风险；同步时区分事实、判断、责任和下一步。
- 不通过无偿定制和无限服务掩盖产品或交付问题，关注成本与可持续性。
- 涉及客户数据、账号、日志和生产环境时，遵守授权、最小权限、保密与安全要求。
- AI 用于客服总结、风险预测、方案生成或自动回复时，需校验事实、权限和输出，保留人工复核与升级通道。
- 本方法论仅用于兜底结构，不覆盖用户事实、合同条款、客户内部情况、公司交付制度和真实产品能力。
